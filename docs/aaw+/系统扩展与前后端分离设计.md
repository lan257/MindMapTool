
### **4.1 设计背景**

本系统初期以**单机版工具模式**为主，用户在本地运行 Avalonia 应用，通过 SqlSugar 操作 SQLite 数据库，实现导图的编辑与存储。  
随着功能扩展与数据规模增加，未来系统可能演化为**前后端分离架构**，前端使用 Avalonia 或 Web 应用，后端基于 ASP.NET Core WebAPI 提供统一的数据访问接口。

在这种演化过程中，必须保证系统具备以下能力：

- **前后端访问方式可切换**（本地数据库与远程服务器间自由转换）；
    
- **界面与业务逻辑层解耦**，避免因模式切换而重写业务代码；
    
- **可扩展性强**，能无缝接入新数据源（如 Neo4j、云同步、文件系统等）。
    

为此，系统设计了一套**“双层仓储 + 策略切换”架构**，实现数据访问方式的统一封装与可扩展切换。

---

### **4.2 问题分析**

在多数据源（本地 / 远程）共存场景下，若为每张表编写单独的访问逻辑（如 MindMap1、MindMap2、Node1、Node2），会造成以下问题：

1. **代码重复**：接口与逻辑高度重合，维护困难；
    
2. **扩展代价高**：新增数据表需同时修改多个类；
    
3. **类型不统一**：无法保证前端调用的一致性；
    
4. **难以维护**：后期修改需双向同步，增加出错风险。
    

因此，必须通过统一接口与策略化切换来解决这一问题。

---

### **4.3 设计目标**

系统在扩展前后端分离时，应实现以下设计目标：

1. **统一访问入口**：所有数据访问均通过统一接口进行；
    
2. **模式可切换**：可在运行时或配置文件中切换“本地 / 远程”模式；
    
3. **实现解耦**：前端与业务层不依赖底层实现；
    
4. **高扩展性**：支持后续引入更多数据源；
    
5. **性能可控**：在保持结构清晰的同时，确保访问效率。
    

---

### **4.4 设计方案**

#### **4.4.1 总体思路**

采用“**双层仓储 + 策略切换**”架构，即：

|层级|职责|
|---|---|
|**通用仓储层（IRepository<T>）**|提供统一的增删改查（CRUD）接口|
|**专用仓储层（INodeRepository、IMindMapRepository 等）**|为复杂实体定义独有的业务方法|
|**数据提供器层（IDataProvider）**|聚合所有仓储实例，对外提供统一访问接口|
|**业务逻辑层（Service）**|封装跨表、批量或事务性操作，组合多个仓储实现业务功能|

通过这一分层设计，系统实现了本地与远程模式下访问逻辑的完全分离，  
同时保证了上层模块（如 ViewModel、UI）逻辑不受影响。

---

#### **4.4.2 通用仓储接口**

```csharp
public interface IRepository<T> {
    Task<T?> GetAsync(int id);
    Task<List<T>> GetAllAsync();
    Task<int> AddAsync(T entity);
    Task UpdateAsync(T entity);
    Task DeleteAsync(int id);
}
```

此接口定义了所有数据表通用的基本操作，为各表提供统一访问规范。

---

#### **4.4.3 专用仓储接口**

对复杂实体（如节点 Node）建立扩展接口，以支持额外业务逻辑：

```csharp
public interface INodeRepository : IRepository<Node> {
    Task<List<Node>> GetChildrenAsync(int parentId);
    Task<List<Node>> GetTreeAsync(int mapId);
}
```

不同实体可拥有各自扩展方法，从而保持灵活性与高内聚性。

---

#### **4.4.4 本地与远程实现**

- **LocalRepository / LocalNodeRepository**：  
    使用 SqlSugar 操作 SQLite，执行本地数据访问；
    
- **RemoteRepository / RemoteNodeRepository**：  
    使用 HttpClient 访问 WebAPI 接口，实现远程访问逻辑。
    

两者的接口结构保持一致，可在运行时自由切换。

---

#### **4.4.5 数据提供器（统一入口）**

所有数据访问通过 `IDataProvider` 进行聚合：

```csharp
public interface IDataProvider {
    IRepository<MindMap> MindMaps { get; }
    INodeRepository Nodes { get; }
    IRepository<NodeRelation> NodeRelations { get; }
}
```

实现类 `LocalDataProvider` 与 `RemoteDataProvider` 分别实例化对应的仓储。

系统启动时通过 `DataProviderFactory` 选择模式：

```csharp
public static class DataProviderFactory {
    private static IDataProvider? _current;

    public static void Initialize(bool useRemote, string? remoteUrl = null) {
        _current = useRemote
            ? new RemoteDataProvider(new HttpClient { BaseAddress = new Uri(remoteUrl!) })
            : new LocalDataProvider(new SqlSugarClient(...));
    }

    public static IDataProvider Current => _current ?? throw new Exception("DataProvider 未初始化");
}
```

---

#### **4.4.6 上层统一调用**

UI 层或 ViewModel 层无需关心后端实现方式：

```csharp
var dp = DataProviderFactory.Current;
await dp.Nodes.DeleteAsync(5);
var map = await dp.MindMaps.GetAsync(2);
```

在“单机模式”下调用本地 SQLite，在“远程模式”下自动访问 WebAPI。  
业务代码完全一致，架构具有良好的稳定性与扩展性。

---

### **4.5 优点分析**

|优点|说明|
|---|---|
|**统一接口**|所有模块通过相同入口访问数据|
|**灵活切换**|模式切换仅需一处配置修改|
|**低耦合**|UI 层与数据实现完全解耦|
|**扩展性强**|新增数据源仅需实现对应仓储|
|**可维护性好**|逻辑清晰，层次分明，结构稳定|
|**平滑升级**|单机版可无缝过渡至前后端分离版|

---

### **4.6 实施建议**

1. **开发阶段**
    
    - 初期仅实现本地仓储（LocalRepository），完成核心功能；
        
    - 后期根据需要增加 RemoteRepository，并补充 WebAPI 接口。
        
2. **运行模式控制**
    
    - 通过配置文件 `config.json` 控制系统运行模式：
        
        ```json
        { "UseRemote": false, "ApiUrl": "http://localhost:5000" }
        ```
        
    - 程序启动时自动读取配置并初始化数据提供器。
        
3. **复杂业务扩展**
    
    - 复杂逻辑应封装于 Service 层，而非仓储层；
        
    - 在 Service 层组合多个仓储实现批量、事务等功能；
        
    - 确保数据操作的原子性与性能。
        

---

### **4.7 结论**

通过“**双层仓储 + 策略切换**”架构设计，  
系统在保持轻量化与高性能的同时，实现了前后端解耦与访问方式统一。  
该方案不仅满足单机工具版的使用需求，也为未来的云同步、多人协作与 AI 知识网络化奠定了架构基础。

这种设计理念兼顾**实用性、可维护性与演化潜力**，是从单机系统向分布式知识管理平台平滑过渡的关键结构。
